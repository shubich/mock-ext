## Фаза 1 — Must-have (ежедневное использование)

Важно, когда MockWeave используется постоянно или конфиги шарятся в команде.

### 1. Экспорт / импорт правил (JSON)

**Зачем:** Правила только в `chrome.storage.local` одного профиля. Нет бэкапа, шаринга, переноса на другую машину.

**Объём:**

- Экспорт всех правил в `.json`
- Импорт из файла (merge или replace — выбрать в UI)
- Тот же формат, что в `service_worker.js`
- Точки входа: тулбар **Правила** в DevTools (и опционально popup)

### 2. Изменение порядка правил + дубликат

**Зачем:** Срабатывает первое совпадение. Новые правила в начало (`unshift`), но при 10+ правилах приоритет неудобно менять.

**Объём:**

- Вверх / вниз (или drag-and-drop) в таблице правил
- Опционально: **Дублировать правило** в редакторе
- Подсказка в UI: «Срабатывает первое подходящее правило — порядок важен»

### 3. Синхронизация popup ↔ DevTools и целевая вкладка

**Зачем:** Два UI редактируют одно хранилище, но ведут себя по-разному.

**Известные проблемы:**

- Popup включает моки для **активной** вкладки; DevTools — для **inspected**. Легко переключить не ту вкладку.
- Popup не слушает `chrome.storage.onChanged` для `rules`; DevTools слушает. Autosave popup через `UPSERT_RULES` может перезаписать правки из DevTools, если оба окна открыты.

**Объём:**

- Popup перечитывает правила при изменении `rules` в storage
- Безопаснее сохранять: merge по `id`, а не полная замена (или предупреждение)
- Показывать, какая вкладка под контролем; предупреждать при расхождении с inspected tab

### 4. Валидация правил в редакторе DevTools

**Зачем:** В popup regex проверяется при сохранении; в DevTools — нет. Битый regex тихо пропускается в runtime (`matchRule` в `service_worker.js`).

**Объём:**

- Проверка компиляции regex при Create / Save в DevTools
- Статус для включённых правил с невалидным шаблоном
- Опционально: tooltip в Захвате с id / pattern сработавшего правила

### 5. Минимальные тесты + CI

**Зачем:** Нет страховки для matching, curl parser, CORS.

**Объём:**

- Вынести чистые функции (`matchRule`, `parseUrlMatcher`, `parseCurlCommand`, `withDefaultCorsHeaders`)
- Unit-тесты на Node
- GitHub Action: lint + test на push/PR

## Фаза 2 — Nice-to-have (паритет с аналогами)

Не обязательно для solo local dev, но часто есть в похожих инструментах.

| Фича | Зачем |
|------|--------|
| Совпадение по HTTP method | Один URL — разные моки для GET и POST |
| Совпадение по headers / query | Точнее без длинных URL |
| Задержка ответа (мс) на правило | Медленный API |
| Имена правил / теги | Поиск в длинном списке |
| Badge на иконке при включённом перехвате | Видно без popup |
| HAR → правила (bulk) | Моки из записи |
| Переменные (`{{baseUrl}}`, `{{token}}`) | Меньше копипасты |
| Format / validate JSON в textarea | Меньше ошибок при сохранении |
| Диалоги вместо `prompt` / `confirm` | Надёжнее в extension context |
| `chrome.storage.sync` или export в git | Несколько машин / команда |

## Сознательно вне scope (пока)

Ограничения CDP или продукта — не планируем без смены требований.

| Тема | Причина |
|------|---------|
| Скрыть моки из Network tab | CDP не убирает строки; описано в README |
| Полная замена Postman | Send закрывает replay, не API-клиент |
| WebSocket / SSE | Только HTTP `Fetch` |
| Бинарные / image моки | Сейчас текст/UTF-8 |
| Cloud sync / workspaces | Local-first; export/import достаточно для v1 |
| Firefox и др. браузеры | Только Chrome MV3 |

## Известные ограничения (не баги roadmap)

- Захват только в памяти (макс. 200, дедуп по method + URL)
- Body ответа обрезается ~1 MB (захват, Send, direct HTTP)
- В Network **Response** часто пусто для fake mock — норма для CDP
- Жёлтая полоса `chrome.debugger` (dev: `--silent-debugger-extension-api`)
- Сохранённые запросы: лимит 100 в `service_worker.js`
- curl: нет `@file` для body
